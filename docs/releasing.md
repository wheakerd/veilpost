# Development commands and releases

English | [简体中文](releasing.zh-CN.md)

The Makefile in the repository root is the shared entry point for local development and GitHub Actions. The frontend still uses Node 26.13.1 and Bun 1.4.4; the backend uses Go 1.27.4. The exact versions are read from `app/frontend/.nvmrc`, `app/frontend/package.json`, and `app/backend/.go-version` respectively.

## Development and checks

`make start` / `stop` / `restart` / `status` / `logs` manage this project's Docker Compose services. In Compose, the backend trusts client addresses forwarded by the frontend proxy within the private network range (`VPN_TRUSTED_PROXIES`); this is for development only. The frontend is mapped to local port 3000 by default, and the backend host port is assigned dynamically; containers reach each other through the service name `backend:8080`. `FRONTEND_PORT=0` picks a random mapping for the frontend, and `OPEN_BROWSER=false` stops the host browser from opening automatically.

On first use, run `make admin-create`: in a terminal you enter the username and password interactively; in a non-interactive environment a random password is generated automatically and the username defaults to `admin`. To generate one explicitly, use `make admin-create GENERATE_PASSWORD=1 USERNAME=admin`. This command uses the shell directly and does not depend on Python; all credentials are passed to the backend on standard input and never appear on the command line. Real accounts and sessions are stored in the `auth-data` named volume, and rebuilding or stopping containers does not delete the data. Backups must include the SQLite file and `master.key`; do not use `docker compose down -v` to clear development data.

Frontend source is mounted into the container with HMR support; after backend changes, run `make restart` to rebuild. The VPN deployment reference configuration in `docker/soft-router/` is not part of this stack.

## Install on a Linux host

Use the release archives that match the host architecture (`amd64` or `arm64`). Verify the downloaded archives against `SHA256SUMS` before extracting them.

1. Run `veilpost-api` under a dedicated account through the host service manager. Use a persistent data directory such as `/var/lib/veilpost`. [Backend configuration](../app/backend/README.md#configuration)
2. Serve the frontend static assets over HTTPS with a History fallback. Proxy `/api/` to the backend and configure `VPN_PUBLIC_ORIGIN` and `VPN_TRUSTED_PROXIES` for the deployment. Set the proxy read timeout above 25 seconds for agent long polls.
3. Run `veilpost-agent` directly on each node host. Register the node's signed APT package sources when enabling Docker Engine installation. [Node agent setup](../app/agent/README.md)

## Creating an administrator in production

The Linux backend release package includes `admin-create.sh`, which runs when placed in the same directory as `veilpost-api`. Use the backend service's data directory and service user:

```bash
VPN_DATA_DIR=/var/lib/veilpost GENERATE_PASSWORD=1 USERNAME=admin sh ./admin-create.sh
```

If the backend binary is somewhere else, add `VPN_API_BIN=/path/veilpost-api`. The script does not need Python, Node, the Go SDK, Docker, or Make (native binary mode); by default credentials are saved in `.runtime/admin-credentials/` in the script directory, and `VPN_CREDENTIALS_DIR` can point to another writable private directory. Account creation never resets an existing password.

If you forget the password, or lose the verifier and all recovery codes, use the same script for local recovery; both actions revoke all sessions of the account:

```bash
VPN_DATA_DIR=/var/lib/veilpost ADMIN_ACTION=reset-password GENERATE_PASSWORD=1 USERNAME=admin sh ./admin-create.sh
VPN_DATA_DIR=/var/lib/veilpost ADMIN_ACTION=reset-two-factor USERNAME=admin sh ./admin-create.sh
```

When the backend is deployed behind a reverse proxy, set `VPN_TRUSTED_PROXIES` to the proxy address (IP or CIDR) so that sign-in rate limiting applies to the real client.

The random password is generated by the system [OpenSSL rand](https://docs.openssl.org/master/man1/openssl-rand/), which reads 32 random bytes and outputs 64 hexadecimal characters. The credential file has permissions `600` and its directory `700`, and the plaintext is not printed to the terminal; save it to a password manager and then delete the file.

When required commands are missing, the script reads `/etc/os-release` (or `/usr/lib/os-release`), installs OpenSSL/coreutils, checks again, and continues: Debian/Ubuntu use apt-get, the Fedora/RHEL family uses dnf/yum, Alpine uses apk, the Arch family uses pacman, and openSUSE/SLES use zypper. Only the packages for the missing tools are installed, without a full system upgrade or a change of package sources; on Arch the existing sync database is used, and if it is outdated the administrator must maintain the system first. Installation uses root or sudo, and non-interactive mode requires `sudo -n` to work; an unsupported distribution, insufficient permissions, tools still missing, or a failed installation all exit with a clear error and do not go on to create the account.

## Checks and packaging

```bash
make install
PLAYWRIGHT_CHANNEL=chrome make check
make build
make release VERSION=v0.1.0
```

Native checks need the pinned versions of Go, Node, and Bun, plus GNU Make, Python 3.11+, and a C compiler. Browser tests use four workers by default, on port 4173 and a random backend port; they verify against the real Go/SQLite service without API mocks. Temporary test accounts, databases, and keys are destroyed after the tests finish. To install the browser for the first time, run `bunx playwright install chromium` in app/frontend. `make build` writes the frontend output to `dist/frontend/` in the repository root and produces `app/backend/bin/veilpost-api` and `app/agent/bin/veilpost-agent`.

On Linux with `flock`, use `make native-start`, `make native-stop`, `make native-restart`, `make native-status`, and `make native-logs` to manage the native stack. The Go backend controller calls the TypeScript frontend launcher under the same development lock. Use `make -C app/backend dev-start` and the corresponding `dev-stop`, `dev-restart`, `dev-status`, or `dev-logs` targets to manage just the backend. Native development uses a separate database from Compose. Stop the current stack before switching modes to free the frontend port.

## Release artifacts

Versions of the form `vMAJOR.MINOR.PATCH` are supported, including ones with a prerelease identifier such as `v0.1.0-rc.1`; leading zeros, paths, whitespace, and `+...` build metadata are not accepted.

```text
dist/releases/v0.1.0/
  veilpost-v0.1.0-frontend.tar.gz
  veilpost-v0.1.0-linux-amd64.tar.gz
  veilpost-v0.1.0-linux-arm64.tar.gz
  veilpost-v0.1.0-agent-linux-amd64.tar.gz
  veilpost-v0.1.0-agent-linux-arm64.tar.gz
  manifest.json
  SHA256SUMS
```

- The frontend package contains only the `frontend/` static directory from the production build, without source directories or node_modules.
- The two backend packages contain the CGO-free Linux `veilpost-api`, the standalone administrator initialization script `admin-create.sh`, a non-sensitive configuration example, and this document. Go builds with `-trimpath` and writes the version and commit through linker flags; run `./veilpost-api --version` to see them.
- The two agent packages contain the CGO-free Linux `veilpost-agent` and its documentation, for use on node servers; they also carry the version and commit, shown by `./veilpost-agent version`.
- `manifest.json` records the version, commit, commit time, working tree state, and the SHA-256 of each package; `SHA256SUMS` covers the five archives and the manifest.
- Archives use sorted files, fixed permissions, and the commit time, and carry no machine paths, file owners, or generation time; symbolic links are rejected. The same version, commit, source files, and toolchain produce identical archives.
- Only explicitly listed build files are packaged, without `.env`, run records, copies of VPN configuration, or keys. `backend.env.example` is only a reference, and the program does not load it automatically.

Locally, preview packages can be built from an uncommitted working tree, but the manifest marks them `dirty: true` and the publish script refuses to upload them. CI packaging requires a clean working tree and a version tag pointing at the current HEAD. An existing output directory is never overwritten; to verify the same version again, specify another ignored directory, for example:

```bash
RELEASE_DIR=.runtime/release-preview make release VERSION=v0.1.0-rc.1
```

The backend package runs directly after extraction:

```bash
sha256sum --ignore-missing --check SHA256SUMS
tar -xzf veilpost-v0.1.0-linux-amd64.tar.gz
./veilpost-api --version
VPN_HTTP_ADDR=127.0.0.1:8080 VPN_DATA_DIR=/var/lib/veilpost VPN_PUBLIC_ORIGIN=https://console.example ./veilpost-api
```

The release workflow publishes the archives for installation on Linux hosts. [Host installation](#install-on-a-linux-host)

## GitHub Actions

### CI

`.github/workflows/ci.yml` runs on branch pushes, pull requests, and manual triggers, and is also reused by the release workflow. It uses Ubuntu 24.04, the toolchain versions pinned in the repository, and Playwright Chromium, and runs:

1. `make install` to install locked dependencies.
2. Install Chromium and the browser's system dependencies on the runner.
3. Check the workflows with a pinned version of actionlint.
4. `make check` and `make build`.
5. On failure, keep the browser diagnostic artifacts for 7 days.
6. Smoke-test authentication and persistence against a disposable Compose stack.

GitHub Actions discovers workflow YAML under `.github/workflows/`. On other CI platforms, install the pinned toolchains and Playwright Chromium in the runner, then run `make install`, `make check`, and `make build` from the repository root. Runners with Docker can add the disposable Compose smoke test.

### Automatic release

`.github/workflows/release.yml` is triggered by pushing a `v*` tag; tags that do not match the version format above fail and are not published.

1. Reuse the full CI; packaging starts only after it passes.
2. Build five archives (the frontend, the backend for two architectures, and the node agent for two architectures) from a clean checkout of the tagged commit and upload them as a temporary Actions artifact.
3. A separate publish job downloads the artifacts and checks again that the manifest, SHA-256, version, and tag commit are consistent.
4. The GitHub CLI creates the Release, attaches all seven files (the five archives, `manifest.json`, and `SHA256SUMS`), and generates release notes. Versions with a suffix such as `-rc.1` are published as prereleases and are not marked Latest.

All external Actions are pinned to full commit SHAs, with the version recorded in a comment. The check and packaging jobs have only `contents: read`; only the publish job gets `contents: write`, and only the publish step sets `GH_TOKEN`. The workflow uses the `GITHUB_TOKEN` that GitHub provides automatically, so no personal access token is needed. The repository or organization must allow these Actions and the requested release permissions.

First commit the code and workflows and push the commit to the repository, then create and push the version tag:

```bash
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin refs/tags/v0.1.0
```

The automation never creates or moves Git tags and never overwrites an existing Release. The GitHub CLI first creates a draft, uploads the assets, and publishes it after they succeed; if an interrupted upload leaves a draft behind, review and clean up that failed draft manually before rerunning, so that no existing version is overwritten.

## Local pre-release verification

After building release packages on a clean, version-tagged commit, you can run a fully local pre-release check:

```bash
VERSION=v0.1.0 GITHUB_REPOSITORY=wheakerd/veilpost \
  python3 scripts/publish.py --dry-run
```

This command does not contact GitHub. An actual manual release uses `GITHUB_REPOSITORY=wheakerd/veilpost make publish VERSION=v0.1.0` and needs a signed-in GitHub CLI or a `GH_TOKEN` with appropriate permissions; the remote tag must already exist.

Local checks do not prove that GitHub-hosted runners have run successfully. The first remote release still requires checking the Actions results and the Release attachments after committing and pushing the workflows.
